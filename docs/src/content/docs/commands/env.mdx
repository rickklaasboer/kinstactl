A site has a live environment and optionally one or more staging environments. The `env` commands manage those environments and move content between them. For actions on the whole site, see [sites](/commands/sites/).

```sh
kinstactl env list klant-x
kinstactl env clone klant-x dev --from live
kinstactl env push klant-x --from staging --to live
```

Commands that change an environment wait for Kinsta to finish by default, and accept `--no-wait`, `--timeout <minutes>` and `--dry-run`; see [operations](/commands/operations/). `--dry-run` prints the resolved target and the request that would be sent, and changes nothing.

## env list

List the environments of a site.

```sh
kinstactl env list klant-x
```

<CommandRef path="env list" />

Use it to find the names you pass to `--env` on other commands.

## env push

Push the database and/or files of one environment to another.

```sh
kinstactl env push klant-x --from staging --to live
```

<CommandRef path="env push" />

`--to` is overwritten with the content of `--from`, so the command asks for confirmation first. On a terminal you answer a prompt. In a script, pass `--yes`, otherwise it fails with `CONFIRMATION_REQUIRED` (exit code 5). Without `--from` or `--to`, a terminal asks which environment you mean; in a script both are required, and they must be different environments.

By default the database and all files are pushed, and a search and replace is run on the database. Narrow that down with the `--no-` options:

```sh
kinstactl env push klant-x --from staging --to live --no-db --path wp-content/themes --yes
```

- `--no-db` and `--no-files` skip one half of the push. Pushing neither is a `USAGE` error.
- `--no-search-replace` skips that search and replace.
- `--path` pushes only the given files or folders instead of all files, and cannot be combined with `--no-files`.

## env create

Create a new environment for a site.

```sh
kinstactl env create klant-x dev --admin-user admin --admin-email admin@klant-x.nl --admin-password -
```

<CommandRef path="env create" />

By default the new environment gets a fresh WordPress install, so it needs the admin user, email and password, like [`sites create`](/commands/sites/#sites-create). Pass `--plain` for an empty environment without WordPress, and `--premium` for a premium staging environment.

## env clone

Clone an environment into a new environment of the same site.

```sh
kinstactl env clone klant-x dev --from live
```

<CommandRef path="env clone" />

This is the quickest way to get a staging copy of live. To clone into a new site instead of a new environment, use [`sites clone`](/commands/sites/#sites-clone).

## env delete

Delete an environment.

```sh
kinstactl env delete klant-x --env staging --confirm klant-x
```

<CommandRef path="env delete" />

Deleting an environment cannot be undone, so `--yes` is not accepted. Confirm by typing the site name when prompted, or pass it as `--confirm <site-name>` in a script. Run it with `--dry-run` first to check which environment is selected.

## env php-allocation

Change the PHP allocation of a premium staging environment.

```sh
kinstactl env php-allocation klant-x --env staging --threads 4 --memory 256
```

<CommandRef path="env php-allocation" />

This is only for premium staging environments. The allocation of the live and the standard staging environment is changed per site with [`sites php-allocation`](/commands/sites/#sites-php-allocation).

## env webroot

Change the webroot subfolder of an environment.

```sh
kinstactl env webroot klant-x /public --env live
```

<CommandRef path="env webroot" />

Use this when the site should be served from a subfolder such as `/public`. Pass `/` to serve from the root again. After the change kinstactl clears all caches and refreshes the plugin and theme inventory, unless you pass `--no-clear-cache` or `--no-refresh`.

## env files

Show the file tree of an environment.

```sh
kinstactl env files klant-x --env live
```

<CommandRef path="env files" />

Handy to check which paths exist before you use `--path` with `env push`.
